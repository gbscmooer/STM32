# WebSocket vs MQTT+HTTP 资源分析

## 当前方案（MQTT + HTTP）

### 内存占用
| 项目 | 大小 | 说明 |
|------|------|------|
| 图像缓冲区 (80×60) | 4,800 字节 | 灰度图像 |
| ESP8266接收缓冲区 | 2,048 字节 | strEsp8266_Fram_Record.Data_RX_BUF |
| MQTT发送缓冲区 | ~200 字节 | JSON数据 |
| HTTP Header | ~150 字节 | POST请求头 |
| FreeRTOS堆 | 15,360 字节 | 15KB |
| Malloc池 | 10,240 字节 | 10KB |
| **总计** | **~32KB** | **可用（STM32F103有64KB SRAM）** |

### 程序流程
```
1. MQTT连接 → 发布数据 → 断开 (5秒)
2. HTTP连接 → 上传图像 → 断开 (8秒)
3. 等待2秒 → 重连MQTT → 循环
总周期: ~15秒
```

### 优点
- ✅ MQTT轻量级（QoS 0）
- ✅ HTTP简单可靠
- ✅ 顺序执行，ESP8266压力小

### 缺点
- ❌ 需要频繁断开/重连
- ❌ 图像需要下采样（160×120 → 80×60）
- ❌ 响应延迟大（最差15秒）

## WebSocket方案

### 内存占用估算

| 项目 | 大小 | 说明 |
|------|------|------|
| **图像缓冲区 (160×120)** | **19,200 字节** | **全分辨率灰度** |
| WebSocket帧头 | 14 字节 | 完整帧头（含掩码） |
| ESP8266接收缓冲区 | 2,048 字节 | 保持不变 |
| WebSocket握手缓冲区 | ~512 字节 | HTTP升级请求/响应 |
| WebSocket发送缓冲区 | ~256 字节 | 传感器数据JSON |
| FreeRTOS堆 | 15,360 字节 | 保持15KB |
| Malloc池 | **25,600 字节** | **需扩大到25KB** |
| **总计** | **~63KB** | **接近极限（64KB SRAM）** |

### WebSocket协议开销

#### 1. 握手阶段（HTTP Upgrade）
```http
客户端请求 (~200字节):
GET /ws HTTP/1.1
Host: 47.83.221.161:6637
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

服务器响应 (~150字节):
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

#### 2. 数据帧格式
```
传感器数据帧 (~70字节 JSON + 6字节帧头):
[FIN=1][Opcode=1][Mask=1][Len=70][4字节掩码][Payload]

图像数据帧 (19200字节 + 14字节帧头):
[FIN=1][Opcode=2][Mask=1][Len=126][2字节扩展长度][4字节掩码][Payload]
```

#### 3. 心跳帧（Ping/Pong）
```
每30秒一次 (~6字节):
[FIN=1][Opcode=9][Mask=1][Len=0][4字节掩码]
```

### 传输效率对比

#### 当前方案（MQTT+HTTP）
```
传感器数据: 
  MQTT固定头(2) + 可变头(7) + Topic长度(15) + Payload(70) = 94字节

图像数据:
  HTTP Header(138) + 图像(4800) = 4938字节
  
总计: 94 + 4938 = 5032字节
```

#### WebSocket方案
```
传感器数据:
  帧头(6) + Payload(70) = 76字节  (-18字节)

图像数据:
  帧头(14) + 图像(19200) = 19214字节  (+14276字节)
  
总计: 76 + 19214 = 19290字节  (+283% !)
```

### 代码复杂度

#### 需要实现的功能
1. **WebSocket握手** (~200行)
   - HTTP Upgrade请求构造
   - Base64编码（Sec-WebSocket-Key）
   - SHA-1哈希验证（可选）
   - 响应解析

2. **WebSocket帧封装** (~150行)
   - 帧头构造（FIN, Opcode, Mask, Length）
   - 掩码生成（4字节随机数）
   - Payload掩码处理（XOR运算）
   - 分片处理（大数据）

3. **WebSocket帧解析** (~200行)
   - 帧头解析
   - 控制帧处理（Ping/Pong/Close）
   - 分片重组
   - 反掩码（如果服务器发送掩码帧）

4. **心跳维护** (~50行)
   - 定时发送Ping
   - 响应Pong
   - 超时检测

5. **重连机制** (~100行)
   - 连接断开检测
   - 自动重连
   - 指数退避

**总计: ~700行新增代码**

### 程序流程
```
1. WebSocket握手 (一次性)
2. 持续连接：
   - 每10秒发送传感器数据帧
   - 每10秒发送图像数据帧
   - 每30秒发送心跳帧
   - 实时接收控制命令
```

## 结论与建议

### ⚠️ **WebSocket方案存在重大风险**

#### 1. **内存风险（关键）**
```
STM32F103 SRAM: 64KB
WebSocket方案需求: ~63KB
剩余空间: <1KB

风险:
- 栈空间不足（中断、函数调用可能失败）
- 无法处理临时变量
- 系统崩溃概率高
```

#### 2. **ESP8266带宽风险**
```
当前方案: 5KB / 15秒 = 333 字节/秒
WebSocket: 19KB / 10秒 = 1900 字节/秒

ESP8266 UART: 115200 bps = 11.5 KB/秒（理论）
实际可用: ~8 KB/秒（考虑协议开销）

19KB图像传输时间: 19200 / 8000 = 2.4秒

风险:
- 传输时间长，阻塞其他操作
- AT指令缓冲区可能溢出
- 传输失败率上升
```

#### 3. **实现复杂度高**
- 需要完整的WebSocket协议栈
- 掩码/反掩码处理（每字节XOR）
- 分片/重组逻辑
- 调试困难（二进制协议）

```
优势:
- 内存安全（<40KB）
- 代码稳定（已测试）

```

```
- 内存安全（~35KB）
- MQTT实时响应（<1秒）
```
